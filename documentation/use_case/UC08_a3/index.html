    UC08 - A3 Module Tools (ontobdc a3)

    Description

    This use case covers the complete operational flow of the A3 module in OntoBDC. The command group ontobdc a3 is responsible for:

    • ingesting a text source into the A3 lifecycle area;
    • organizing the source as a deterministic package;
    • advancing the package through the A3 state machine;
    • generating intermediate artifacts for each processing stage;
    • validating the RDF output against SHACL; and
    • dispatching the final result as event.jsonld.

    The current A3 pipeline is artifact-driven. A package advances physically according to the files found in its lifecycle directory, which also allows execution to resume from the most advanced completed step.

    Actors

    • User: Wants to ingest a source and process it through the A3 extraction pipeline.
    • System (OntoBDC): Validates module availability, accepts the source, persists the package, evaluates package state from artifacts, executes the corresponding transformation capabilities, and reports success or failure.

    Pre-conditions

    • The project is initialized.
    • The A3 extra is enabled in the current environment: ontobdc extra --enable a3.
    • The runtime environment can access the lifecycle directory used by A3.
    • When the parsed and validated stages are reached, the environment must also support:
    • network access to retrieve the ontology and SHACL shape;
    • the configured LLM CLI used by the parser capability; and
    • pyshacl installed as part of the A3 dependencies.

    Commands

    Help

    • ontobdc a3
    • ontobdc a3 --help
    • ontobdc a3 -h

    Displays the A3 help menu after verifying that the module is enabled.

    Ingestion

    • ontobdc a3 --etl --source <file|url>

    Creates or reuses a lifecycle package from the provided source and persists the original textual content as raw.txt.

    Processing

    • ontobdc a3 --work

    Scans all lifecycle packages and processes them concurrently, one worker per package, until each package reaches a final state or an error interrupts execution.

    Main Flow

    1. The user runs ontobdc a3 --etl --source <file|url>.
    2. The system verifies that the A3 module is enabled.
    3. The system validates that --source was provided.
    4. The system resolves a compatible extraction strategy for the source.
    5. The system extracts the source content.
    6. If the extracted resource is textual, the system normalizes it into an A3 raw text resource.
    7. The system computes a deterministic package identifier from the normalized content.
    8. The system writes raw.txt inside the lifecycle package directory.
    9. The system reports that the ETL start succeeded.
    10. The user runs ontobdc a3 --work.
    11. The system lists all packages in the lifecycle directory.
    12. The system creates one A3 worker per package and executes them concurrently.
    13. Each worker evaluates the package state by inspecting existing artifacts on disk.
    14. The worker initializes the A3 statechart from the current physical state.
    15. The worker repeatedly executes the next valid transition until the package reaches the final dispatched state.
    16. For each transition, the system resolves the capability whose identifier targets the destination state and executes it with the package as input.
    17. The system writes the artifact produced by that stage back into the same package directory.
    18. When all workers finish successfully, the system reports the final state of each processed package.

    A3 Lifecycle

    State Sequence

    The current canonical state sequence is:

    undefined -> received -> sanitized -> parsed -> translated -> validated -> reasoned -> dispatched

    Physical State Rule

    The current state of a package is not inferred from metadata or a database record. It is derived from the files found in the package directory. The most advanced recognized artifact determines the package state.

    State Artifacts

    State Required artifact Meaning
    undefined none No known A3 artifact exists yet.
    received raw.txt Original extracted text was stored in the package.
    sanitized sanitized.txt Basic sanitization was completed.
    parsed parsed.json The LLM produced structured JSON validated by the guardrail.
    translated graph.ttl The structured JSON was converted into RDF/Turtle according to the SHACL shape.
    validated validated.txt The RDF graph conforms to SHACL and the validation report was persisted.
    reasoned reasoned.ttl A reasoning placeholder artifact was created from the graph.
    dispatched event.jsonld The package was emitted as a final event payload.

    Stage Behavior

    received -> sanitized

    • Input: raw.txt
    • Output: sanitized.txt
    • Behavior: performs a basic cleanup step, currently removing simple HTML tags from the raw text.

    sanitized -> parsed

    • Input: sanitized.txt
    • Output: parsed.json
    • Supporting output on failure: err.json
    • Behavior:
    • downloads the ontology referenced by the guardrail shape URI;
    • reads the extraction prompt from ontology terms linked through peo:hasPrompt and peo:hasInstruction;
    • builds a constrained output schema from the SHACL-derived guardrail;
    • invokes the configured LLM CLI to extract structured data; and
    • validates the resulting JSON against required fields, types, cardinality, enums, patterns, and closed-shape constraints.

    parsed -> translated

    • Input: parsed.json
    • Output: graph.ttl
    • Behavior:
    • downloads the target shape ontology;
    • reads sh:targetClass and each sh:property;
    • creates the subject URI from the parsed name;
    • converts scalar and array properties into RDF triples; and
    • normalizes enumerated values against sh:in before serialization.

    translated -> validated

    • Input: graph.ttl
    • Output on success: validated.txt
    • Output on failure: err.json
    • Behavior:
    • downloads the SHACL document;
    • validates the RDF graph with pyshacl; and
    • persists the SHACL validation report when the graph conforms.

    validated -> reasoned

    • Input: graph.ttl
    • Output: reasoned.ttl
    • Behavior: creates a reasoning placeholder by copying graph.ttl into reasoned.ttl. No inference engine is executed yet.

    reasoned -> dispatched

    • Input: graph.ttl
    • Output: event.jsonld
    • Behavior:
    • reads the RDF graph;
    • rewrites the primary subject as an event identifier;
    • serializes the result as JSON-LD.

    The event identifier follows this pattern:

    urn:<shape_name_snake_case>:event/<package>/<timestamp>

    For the current job offer flow, the target shape is JobOfferShape, which yields event identifiers such as:

    urn:job_offer:event/<package>/<timestamp>

    Package Persistence

    Lifecycle Directory

    A3 stores packages inside the lifecycle dataset resolved by the current OntoBDC configuration. In practice, this corresponds to the A3 payload lifecycle area under the local configuration directory.

    Package Identity

    The ingestion step computes the package identifier from normalized raw text. The same text therefore maps to the same package directory, which helps avoid duplicate lifecycle roots for identical content.

    Resume Semantics

    ontobdc a3 --work resumes from the most advanced artifact already present in each package. For example:

    • if only raw.txt exists, the package starts at received;
    • if parsed.json already exists, the package resumes from parsed;
    • if event.jsonld exists, the package is already in its final state.

    This also means stale artifacts can change the state perceived by the worker and must be considered during troubleshooting.

    Alternative and Error Flows

    A3 Not Enabled

    1. The user runs any ontobdc a3 command.
    2. The system detects that the A3 extra is not enabled.
    3. The system aborts and instructs the user to run ontobdc extra --enable a3.

    Missing --source

    1. The user runs ontobdc a3 --etl without --source.
    2. The system rejects the call.
    3. The system prints usage guidance with an example.

    Unsupported Extracted Resource

    1. The user provides a source that does not resolve to a text resource.
    2. The system aborts the ETL ingestion.
    3. The current implementation raises NotImplementedError, because only textual resources are supported by A3 ingestion.

    Invalid Package Transition

    1. A worker attempts to run a transition that does not match the package's current physical state.
    2. The target capability rejects the execution.
    3. The worker fails and reports the package-specific exception.

    Parsing Failure

    1. The parser capability cannot proceed, the LLM execution fails, or the generated JSON violates the guardrail.
    2. The system writes err.json with the current state and error message.
    3. The worker aborts processing for that package.

    SHACL Validation Failure

    1. The translated RDF graph does not conform to the SHACL shape.
    2. The system writes err.json with the current state and validation error.
    3. The worker aborts processing for that package.

    Stuck State

    1. A worker executes the state machine but no physical transition occurs.
    2. The system raises a runtime error indicating that the package is stuck at the current state.
    3. The user must inspect the package artifacts and the generated error details.

    Post-conditions

    • After --etl, the source has been materialized as a lifecycle package containing at least raw.txt.
    • After a successful --work, each processed package reaches dispatched.
    • A successfully completed package contains the full trace of intermediate artifacts generated by the pipeline.
    • The final exported event is stored as event.jsonld.
    • If a stage fails, the package preserves its intermediate artifacts and may also contain err.json for diagnosis.
